# 默认关联研究的三个方向

记录日期：2026-10-14。此计划承接 [研究检查点](research-checkpoint-20261013.md) 和 [正常设置流程分析](native-default-association-flow.md)，不把研究假设当作已实现能力。

## 方向一：验证 MakeDefault

优先分析本机 IAssocHandler::MakeDefault 的实现，确认由谁执行写入、是否启动用户界面，以及是否处理 UserChoiceLatest。随后在保持 Defender/UCPD 正常状态的 VM 中验证首次设置和已有默认程序的切换。

成功需要同时满足接口结果、目标新格式 Hash、Shell 有效 ProgID/命令、真实 PDF 打开行为和重启持久性。接口名称或返回 S_OK 本身不证明设置成功。当前未验证，不能给出成功概率或宣称所有原生 API 都不可用。

## 方向二：研究现有宿主

系统 Framework MSBuild 是当前已经完成本机写入验证的方案，先集成到 EXE 并提供 VM 测试包；InstallUtil、Regsvr32、ODBCConf 仅保留已有实验结果。HTA 和工作流编译器路线按告警/用户反馈排除，不通过关闭防护或添加排除使其可用。

候选来自系统正常扩展机制，不是从已取得的运行时允许名单直接枚举。进一步研究优先在 VM 进行，记录驱动/规则版本、宿主签名、实际写入次数和 Defender 结果。

读取实际名单有助于筛选，但不是发现候选的必需前提。需要 [包含策略数据的完整内核内存快照](ucpd-vm-memory-capture-plan.md)，仅内核堆栈通常不足以遍历名单；该采集方案尚未执行。名单默认值、动态数据和实际加载状态仍须区分。

## 方向三：自有 EXE 进程独立写入

目标是在自有进程中通过可使用的授权入口完成设置，不依靠其他用户态宿主代写。原生 C++、无需脚本、无需 MSBuild 与“实际写入发生在自有进程”是不同能力，不能混为一谈。

在 VM 对照用户通过 Windows 设置完成 PDF 默认选择的正常流程，记录实际 writer、调用栈、Hash 输入和 UCPD 判定，寻找授权边界及可调用入口。不是先假定存在一个可插入代码的时机；当前没有证明可利用缺陷或可转移授权令牌存在。

如果代码最终在系统进程内执行，仍依赖系统进程身份，不能计为自有进程独立写入。此次计划不包括 DLL 注入、身份伪装或修改内核判定。

## 顺序与当前交付

三个方向共享证据，顺序为：验证 MakeDefault；按需取得运行时策略并跟踪正常流程；现有宿主作为可测试的备选继续评估。

近期工程交付先实现明确选择的 Framework MSBuild 后端，注册图标序号使用 1，保持旧格式路径独立，并提供支持版本检查、只读校验、失败日志和可搬到 VM 的测试包。未知系统 DLL 必须拒绝调用未经确认的内部地址，包中不替换系统组件、不改变防护配置；跨构建和完整 VM 切换验证由后续测试完成。
